<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser ← External iframe origin | When `videoUrl` is set, the browser loads content from a third-party origin (YouTube or Vimeo). The iframe runs in a separate browsing context, isolated from the parent page by the browser's same-origin policy. |
| Source code ← Developer edit | `videoUrl` is set by a developer editing the source file. It is not user input, not URL-controlled, not query-string-derived. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-02-01 | Spoofing | Iframe loads malicious content if `videoUrl` is misconfigured | accept | `videoUrl` is set in source code by the developer, not by users or query strings. A misconfigured URL is a developer error caught in code review, not a runtime attack surface. The SUMMARY documents that activation requires a known YouTube `/embed/` or Vimeo embed URL. |
| T-03-02-02 | Tampering | Third-party video platform alters embed behavior over time | accept | Standard risk of any external embed. Mitigated by using two well-known platforms (YouTube, Vimeo) with stable embed contracts. No application code depends on the embed's internal behavior. If a platform deprecates its embed format, the developer updates the `videoUrl` constant. |
| T-03-02-03 | Information disclosure | Iframe leaks visitor data to YouTube/Vimeo via referrer, cookies, or analytics | accept | This is intrinsic to using a third-party video embed. The brand decision (D-08) is platform-agnostic embed, accepting standard YouTube/Vimeo telemetry. A future enhancement could add `referrerPolicy="no-referrer-when-downgrade"` or use the `youtube-nocookie.com` variant; this is out of scope for Phase 3 (no PII at risk, content is public marketing). |
| T-03-02-04 | Denial of service | Iframe fails to load (network, blocking, platform downtime) | accept | The iframe is a non-critical embellishment. If it fails to load, the About page still renders its prose content and CTA. `loading="lazy"` ensures the iframe does not block initial page render. No fallback UI is in scope for Phase 3 (component-level fallback is a v2 concern, not BIKE-05 scope). |
| T-03-02-05 | Elevation of privilege | Iframe `allow` attribute grants permissions to a third-party origin | mitigate | The `allow` attribute is set to the YouTube-recommended permission set: `accelerometer; autoplay; clipboard-write; encrypted-media; gyroscope; picture-in-picture`. These permissions are required for the YouTube/Vimeo player to function (autoplay, fullscreen toggle, picture-in-picture). The acceptance criterion verifies the exact `allow` string is present in the component file, blocking any executor from adding wildcard or unnecessary permissions. |
| T-03-02-06 | Repudiation | Activating the video could publish unverified or unauthorized content | accept | Activation requires a developer edit to the source file followed by a deployment. Git history records the change. No runtime mechanism for non-developer activation exists. |

No high-severity threats. The iframe is a passive read-only embed with no data flow back to the application. All threats are accept or mitigated by the locked attribute set.
</threat_model>
